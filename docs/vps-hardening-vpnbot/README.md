# Защита и обновление VPS с vpnbot_extra (для чайника)

Здесь всё, что было сделано 07.11.2026 на сервере с ботом [vpnbot_extra](https://github.com/ugam842-lab/vpnbot_extra)
(Debian 12, всё работает в Docker), оформленное так, чтобы **повторить на другом таком же сервере за 30-40 минут**
и чтобы можно было сказать Claude: «проверь сервер по инструкции».

Проверено на: Debian 12, 1 ядро, ~1 ГБ ОЗУ, бот `vpnbot_extra` (форк ugam842-lab), контейнеры
`php svc ng up ad xr wg1 wp tg hy`.

## Главные правила

1. **Каждый скрипт по умолчанию «пробный»**: без `--apply` он ничего не меняет, только пишет, что сделал бы.
   Сначала запускаете без `--apply`, читаете, потом с `--apply`.
2. **Шаг за шагом, по порядку.** После каждого шага смотрите, что бот отвечает в Telegram.
3. **Не закрывайте рабочее окно SSH**, пока не проверили вход в новом окне (особенно после шага 1).
4. Скрипты сами останавливаются (`[FAIL]`), если что-то выглядит не так, как ожидалось. Это нормально, не обходите проверку, а покажите вывод Claude.
5. Решения владельца (не менять): **права на файлы (`config/*`, `cert_private`, `app/config.php`, `logs`) не трогаем**
   (контейнеры и бот работают с ними под root, сужение прав может сломать логику); **logrotate для nginx-логов не включаем**
   (логи нужны боту для «Анализа подозрительных IP», их чистят через меню бота).

## Что нужно заранее

- Доступ к серверу как `root` (пароль от хостера или консоль в панели).
- Программа для SSH: Windows PowerShell/Terminal (есть `ssh` и `scp`) или MobaXterm.
- Папка бота на сервере: `/root/vpnbot_extra` (если другая, перед командой пишите `BASE=/путь`).
- 10-15 минут «тихого» времени: на шагах 06, 07, 10 контейнеры перезапускаются, бот молчит ~30-60 секунд.
  **Не делайте это в пятницу около 04:20** (еженедельная перезагрузка).

## Шаг 0. Скопировать скрипты на сервер

На своём компьютере (PowerShell), в папке, где лежит папка `scripts`:

```powershell
scp -P 22 -r scripts root@IP_СЕРВЕРА:/root/vps-scripts
```

(`-P 22`: пока порт стандартный; если уже поменяли, укажите свой. Спросит пароль root.)
Затем зайдите на сервер и подготовьте:

```bash
ssh root@IP_СЕРВЕРА
cd /root/vps-scripts
sed -i 's/\r$//' *.sh          # убираем виндовые переводы строк, иначе скрипты не запустятся
chmod +x *.sh
sh audit.sh                    # первый аудит: сколько красного
```

Сохраните вывод аудита («до»). В конце сделаете ещё один («после»).

## Шаг 1. Ключ для SSH и запрет пароля

Это самое важное и единственное, где можно «запереть себя» снаружи. Идём медленно.

**1.1 Создайте ключ на своём компьютере** (если ещё нет), PowerShell:

```powershell
ssh-keygen -t ed25519 -f "$env:USERPROFILE\.ssh\id_ed25519_vps" -C "my-vps"
```

Вопрос про passphrase можно пропустить (Enter) или задать пароль на ключ. Появятся два файла: приватный `id_ed25519_vps`
(**никому не показывать**) и публичный `id_ed25519_vps.pub`.

**1.2 Положите публичный ключ на сервер.** Покажите его: `type "$env:USERPROFILE\.ssh\id_ed25519_vps.pub"`
(одна длинная строка `ssh-ed25519 AAAA... my-vps`). Затем **на сервере** (в окне, где вы под root):

```bash
mkdir -p /root/.ssh && chmod 700 /root/.ssh
echo 'ВСТАВЬТЕ_СЮДА_СТРОКУ_ПУБЛИЧНОГО_КЛЮЧА' >> /root/.ssh/authorized_keys
chmod 600 /root/.ssh/authorized_keys
```

**1.3 Проверьте вход по ключу в НОВОМ окне** (старое не закрывайте):

```powershell
ssh -i "$env:USERPROFILE\.ssh\id_ed25519_vps" root@IP_СЕРВЕРА
```

Пустили без пароля - хорошо. Нет - исправляйте шаг 1.2, дальше не идти.

MobaXterm: Session -> SSH -> Remote host = IP, Specify username = root, Port = порт, вкладка *Advanced SSH settings* ->
*Use private key* -> выбрать `id_ed25519_vps`. Если MobaXterm просит ключ формата .ppk, он сам предложит конвертировать.

**1.4 Включите запрет пароля** (на сервере):

```bash
sh 01-ssh-key-only.sh            # посмотреть
sh 01-ssh-key-only.sh --apply    # применить
```

**1.5 Проверка**: откройте ещё одно новое окно. По ключу пускает, с паролем (`ssh -o PubkeyAuthentication=no root@IP`) - отказ.
Порт SSH скрипт **не меняет**. Менять порт - отдельное решение (не забудьте открыть новый порт в фаерволе хостера до смены).

**Если заперли себя:** у хостера есть «VNC/консоль/Rescue» в панели. Зайдите через неё как root и удалите файл
`/etc/ssh/sshd_config.d/20-hardening.conf`, затем `systemctl reload ssh`.

## Шаги 2-4. Система (безопасно, перезапуска ботов нет)

```bash
sh 02-swap.sh --apply
sh 03-unattended-upgrades.sh --apply
sh 04-ipv6-ifupdown.sh          # сначала посмотрите
sh 04-ipv6-ifupdown.sh --apply
```

Зачем шаг 4: если IPv6 отключён через sysctl, а в `/etc/network/interfaces` остался блок `iface ... inet6`, то при
перезагрузке `ifup` спотыкается об IPv6 и интерфейс может не подняться, то есть после пятничной перезагрузки сервер «пропадёт».
Скрипт закомментирует блок и проверит `ifup -n`. Делает это только если IPv6 реально выключен.


## Шаги 6-7, 10. Обновление образов (контейнеры перезапускаются)

По одному, с паузой на проверку бота в Telegram (`/menu`, отправка любого сообщения):

```bash
sh 06-nginx-alpine.sh --apply     # nginx; перезапуск ng и up
sh 07-php83.sh --apply            # PHP 8.3; перезапуск php и service
sh 10-adguard.sh --apply          # AdGuard; перезапуск ad
```

Как это устроено (чтобы не бояться): сначала собирается **тестовый** образ под другим именем; для PHP проверяются версия,
что модулей не меньше, чем было, `php -l` для каждого файла бота и `qrencode`; для nginx - `nginx -t` на старом и новом
образе, результат должен совпасть; для AdGuard - что новая версия принимает конфиг. Только потом образ подменяется,
перезапускаются только нужные контейнеры (`--no-deps --force-recreate`), а прежний образ остаётся под тегом `backup-ДАТА`.

**Откат** печатается в конце каждого скрипта. Общий принцип:
`docker tag <образ>:backup-ДАТА <образ>:<рабочий тег>` и перезапуск тех же контейнеров; файлы compose/dockerfile лежат
копиями в `/root/vps-fix-backup-ДАТА/`.

Подводные камни, которые уже встретились:
- Alpine 3.20+ не имеет `php81`, только `php83`; `php.ini` монтируется в `/etc/php83/php.ini`; нужен `libqrencode-tools`
  и симлинк `php` - скрипт 07 это учитывает.
- Если у вас версия бота с другими строками в `docker-compose.yml`, скрипт остановится с понятным `[FAIL]`. Не правьте вручную,
  отдайте вывод Claude.

## Шаги 8-9. Починка мелких багов бота

```bash
sh 08-fix-vless-probe.sh --apply
sh 09-fix-bot-texts.sh --apply
```

- 08: в меню vless кнопка проверки ключа всегда писала «не прошла». Причина - строка `awk` с `RS="\r\n\r\n"`
  в `app/traits/UserPortalTrait.php`, ответ после `tr -d '\r'` уже не содержит `\r\n\r\n`. Заменена на `awk 'NF{l=$0} END{print l}'`.
  Исправление действует и для всех существующих и будущих пользователей (скрипт проверки общий).
- 09: в `app/bot.php` русский текст/эмодзи превратились в `?`. Чинятся иконки уведомлений в меню IP и два текста
  («Доступ к торрентам …», «Обмен между пользователями …»). Остальные `????` - в комментариях кода, безвредны.

Обе правки делаются **только если шаблон найден ровно один раз**, затем `php -l`; при ошибке оригинал возвращается.
Копии - в `/root/vps-fix-backup-ДАТА/`.

## Шаг 11. Очистка логов раз в неделю

```bash
sh 11-log-cleanup.sh --apply
```

Устанавливает `/usr/local/sbin/clear-vpnbot-logs.sh` и cron «пятница 04:19» (за минуту до перезагрузки). Чистятся служебные

## Шаг 12. Автозапуск после перезагрузки (делать до первой перезагрузки!)

```bash
sh 12-fix-makefile-fetch.sh --apply
```

После перезагрузки cron выполняет `make r`: он останавливает контейнеры и запускает их заново, но первой строкой
делает `git fetch` с GitHub. Если GitHub просит логин (`could not read Username`), `make` обрывается и **контейнеры остаются
остановленными**, то есть бот лежит до ручного запуска. Скрипт делает fetch нефатальным. Если бот всё же лежит после
перезагрузки: `cd /root/vpnbot_extra && IP=$(hostname -I | cut -d' ' -f1) make u` (после шага 12) покажет причину и поднимет контейнеры.

## Шаг 13. Автозапуск бота после перезагрузки: варианты

```bash
sh 13-autostart.sh              # показать текущее состояние
sh 13-autostart.sh A --apply    # выбрать вариант A (рекомендуется)
```

Как устроено в боте: в `makefile` цель `r` = `d u` (остановить и снова создать контейнеры). Автозапуск - строка в
`crontab` root: `@reboot cd /root/vpnbot_extra && make r` (так же в readme оригинала `mercurykd/vpnbot`, где путь `/root/vpnbot`).
Отдельно в `docker-compose.yml` форка у каждого сервиса стоит `restart: unless-stopped`. **В оригинале этой строки нет**
(у `php` и `service` она закомментирована).

| Вариант | Что настроено | Стартов после reboot | Плюсы | Минусы |
|---|---|---|---|---|
| **A** (наш) | crontab `@reboot make r` + `restart: unless-stopped` | **2** (Docker сам, потом `make r`) | контейнер, упавший сам (OOM), и контейнеры после перезапуска Docker поднимаются автоматически | два сообщения о старте в Telegram, лишняя минута |
| **B** (как оригинал) | crontab `@reboot make r`, `restart:` закомментирован | 1 | один старт, как задумал автор | упавший контейнер сам не встанет; после перезапуска Docker нужен `make r` |
| **C** | только `restart: unless-stopped`, без crontab | 1 | самое простое | при загрузке не выполняется `make u` (конфиги, `ensure_bin`, `push_nodes`); не рекомендуется |

Двойной старт в варианте A не ошибка. Важно, чтобы запись автозапуска была **одна**: на серверах раньше встречалась вторая копия
в `/etc/cron.d/vpnbot-autostart` (с `sleep 40`), из-за неё `make r` запускался дважды. Скрипт 13 её удаляет.
Ни один вариант не работает, если `git fetch` в `makefile` фатален - сначала шаг 12.

## Шаг 14. Статистика трафика пропадает после перезагрузки (делать ДО первой перезагрузки!)

```bash
sh 14-xray-stats-guard.sh --apply          # защита: служба vpnbot-stats-save
sh 14-xray-stats-guard.sh restore          # если счётчики уже обнулились: вернуть из бэкапа (см. ниже), затем с --apply
```

Симптом: в клиентах (подписка, `subscription-userinfo`) и в боте «использовано трафика» вдруг почти ноль, например
3,87 МиБ вместо десятков ГБ. **Это не очистка логов:** файл `config/xray.stats` лежит в `config/`, а очистка трогает только `logs/`.

Причина: каждые 60 с цикл бота (контейнер `svc`) пишет в `xray.stats` блок `session` (живые счётчики xray). Переносит их
в накопительный `global` (`collectSession`) бот только когда сам перезапускает xray. После reboot xray стартует с нуля, бот
затирает `session`, и всё накопленное с прошлого переноса теряется (у нас пропало 18,9 ГБ + 4,4 ГБ на одном сервере).
Ежемесячный сброс (`reset_monthly` в `pac.json`) - отдельная настройка бота, он обнуляет всё осознанно.

Что делает шаг 14: ставит systemd-службу `vpnbot-stats-save`. При выключении системы **до остановки Docker** она останавливает `svc`
(чтобы цикл бота не перезаписал файл), переносит `session` в `global` и обнуляет `session`. Работает и для пятничной
перезагрузки. Проверка после reboot: `journalctl -t vpnbot-stats-save` (запись «session -> global»).

Режим `restore` берёт последний `/root/vpnbot-backup-*.tar.gz` и прибавляет старый `session` из него к `global`. Восстановить
можно только то, что было в бэкапе: трафик между бэкапом и перезагрузкой потерян. Поэтому **делайте бэкап (шаг 5) прямо перед
перезагрузками** и ставьте шаг 14 до первого reboot. Перед ручным `make r` (xray пересоздаётся) запускайте
`sh /usr/local/sbin/vpnbot-collect-stats.sh`.

Что ещё проверено и безопасно очищать: `adguard`, `mtproto`, `nginx_error`, `requests_error`, `unit_error`, `upstream_error`,
`webhook`, `xray_error` - чисто диагностические логи, бот в них только пишет (xray_error его скрипты и сами обнуляют).
Накопительные данные живут в `config/` (`xray.stats`, `pac.json`, клиенты) и в томах Docker (статистика AdGuard, WARP); очистка логов
и `make r` (без `-v`) их не трогают.

## Шаг 15. conntrack: сервер «тупит» под нагрузкой

```bash
sh 15-conntrack.sh              # покажет, что есть и что будет
sh 15-conntrack.sh --apply
```

Симптомы: при большом числе подключений (родственники, друзья, много устройств) VPN и SSH то замирают, то оживают;
в `dmesg -T | grep "table full"` строки `nf_conntrack: table full, dropping packet`.

Причина: ядро записывает каждое соединение, проходящее через сервер, в таблицу conntrack. На VPS с 1 ГБ ОЗУ по умолчанию
**8192 записей**, а запись об установленном TCP-соединении живёт **5 суток** (`nf_conntrack_tcp_timeout_established = 432000`),
даже если клиент давно исчез. Один браузер открывает сотни соединений, несколько клиентов быстро забивают таблицу, и ядро
отбрасывает пакеты новых соединений.

Что делает шаг 15:

| Параметр | Было | Стало | Где записано |
|---|---|---|---|
| `nf_conntrack_max` | 8192 (на 2 ГБ ОЗУ ядро ставит 65536 само) | 65536 | `/etc/sysctl.d/99-conntrack.conf` |
| `nf_conntrack_tcp_timeout_established` | 432000 с (5 суток) | 86400 с (1 сутки) | там же |
| `hashsize` | 8192 | 16384, только если текущий меньше (на 2 ГБ ОЗУ уже 65536, не трогаем) | `/etc/modprobe.d/nf_conntrack-hashsize.conf` |

Цена: ~300 байт на запись, при полностью заполненной таблице 65536 это около 20 МБ ОЗУ. Применяется сразу, **контейнеры не
перезапускаются**, после перезагрузки значения остаются. Скрипт **ничего не уменьшает** (если max или hashsize уже больше, а
таймаут короче, оставляет как есть) и останавливается с `[FAIL]`, если conntrack уже задан в другом файле
(`/etc/sysctl.conf`, `/etc/sysctl.d`, `/etc/modprobe.d`): такие настройки перебили бы наши, объединять надо вручную.
Свои значения: `CT_MAX=131072 CT_TIMEOUT=43200 CT_HASH=32768 sh 15-conntrack.sh --apply`.

Проверка: `sysctl net.netfilter.nf_conntrack_max net.netfilter.nf_conntrack_tcp_timeout_established; cat /proc/sys/net/netfilter/nf_conntrack_count`.
Откат: удалить оба файла и перезагрузить сервер.

## Шаг 16. Сборщик метрик: понять, что было, когда тупило

```bash
sh 16-collector.sh --apply
tail -20 /var/log/vps-collect.log
```

Когда сервер тормозит, измерять уже поздно. Сборщик (`/usr/local/bin/vps-collect.sh`, cron каждую минуту) пишет одну строку:

```
2026-11-07_21:20:01 load=0.13 memav=1199M swap=0M ct=1083/65536 ctdrop=0 psi_cpu=3.75 psi_mem=0.00 psi_io=0.00 tcp=5 tw=0
```

| Поле | Что значит | Тревожный признак |
|---|---|---|
| `load` | средняя нагрузка за минуту | выше числа ядер (`nproc`) долго |
| `memav` | доступная ОЗУ | ниже ~100 МБ |
| `swap` | занятый swap | растёт вместе с падением `memav` |
| `ct=A/B` | записей conntrack занято / максимум | A близко к B |
| `ctdrop` | отброшенных пакетов conntrack с загрузки | любой рост (были потери) |
| `psi_cpu/mem/io` | % времени, когда задачи ждали CPU / память / диск (за 10 с) | держится выше ~10 |
| `tcp`, `tw` | сокетов TCP всего и в TIME_WAIT | резкий рост `tw` |

Как разбирать: узнайте время, когда тупило, и посмотрите минуты вокруг: `grep '2026-11-07_21:3' /var/log/vps-collect.log`
(старые дни: `zgrep ... /var/log/vps-collect.log.*.gz`). Логика вывода: `ct` у максимума или растёт `ctdrop` - упёрлись в conntrack
(поднять `CT_MAX`); падает `memav` и растёт `swap` - не хватает памяти; высокий `psi_cpu` при высоком `load` - не хватает CPU
(1 ядро); высокий `psi_io` - диск. Ротация: ежедневно, 14 копий, сжатие (`/etc/logrotate.d/vps-collect`), ~200 КБ в сутки.
Откат: `rm /usr/local/bin/vps-collect.sh /etc/cron.d/vps-collect /etc/logrotate.d/vps-collect /var/log/vps-collect.log*`.

## Шаг 17. Освободить диск от мусора Docker

```bash
sh 17-docker-cleanup.sh            # покажет, что удалил бы
sh 17-docker-cleanup.sh --apply
```

Показывает `docker system df` и диск до/после. Чистит:

2. **Образы без контейнеров** (ни один работающий или остановленный контейнер их не использует): старые версии после обновлений,

## Шаг 18. Swap 1 ГБ вместо 2 ГБ на маленьком диске

```bash
sh 18-swap-resize.sh               # проверки и план
sh 18-swap-resize.sh --apply       # SWAP_MB=1536 - другой размер
```

На диске 10 ГБ swap 2 ГБ - пятая часть диска, а используется он на десятки МБ (`swappiness=10`). Скрипт делает: `swapoff` ->
новый `/swapfile.new` нужного размера -> `mkswap` -> замена `/swapfile` -> `swapon`; запись в `/etc/fstab` не меняется.
Останавливается (`[FAIL]`), если: занятый swap не помещается в новый размер, мало свободной ОЗУ для безопасного `swapoff`
(нужно больше `2 x занято + 100 МБ`), мало места на диске. Если что-то сломалось после `swapoff`, старый swap включается обратно.
Контейнеры не перезапускаются. На дисках 20+ ГБ и 2 ГБ ОЗУ можно оставить как есть.

## Как мы разбирали «сервер тупит» (07.11.2026), и какие настройки не применяли

Исходный запрос: на VPS с ботом всё хуже работает, когда подключаются родственники и друзья. Мы замерили три сервера
(A: 1 ядро, 1 ГБ ОЗУ, диск 40 ГБ; B: 1 ядро, 1 ГБ, диск 10 ГБ; C: 2 ядра, 2 ГБ, диск 38 ГБ), только чтением:

| Показатель | A | B | C |
|---|---|---|---|
| Нагрузка (load) | 0,01 | 0,07 | 0,12 |
| Доступная ОЗУ | 287 МБ | 296 МБ | 1190 МБ |
| conntrack max (до) | 8192 | 8192 | 65536 |
| Таймаут established (до) | 5 суток | 5 суток | 5 суток |
| 'table full' в журнале ядра (с 27-30.10) | 0 | 0 | 0 |
| OOM (нехватка памяти) | 0 | 0 | 0 |
| Диск (до -> после шагов 17-18) | 21% -> 14% | **84% -> 58%** | 22% -> 18% |

Замер сделан в тихий вечерний момент через 3 часа после перезагрузки, пиковую нагрузку мы не видели. Поэтому подтверждённой
причины «тупит» нет, самая вероятная - conntrack (мало места на A и B + 5 суток на мёртвые сессии), и для неё шаг 15 дёшев и
безопасен. Чтобы поймать причину наверняка, поставлен шаг 16. Перегрузки CPU, памяти, диска и «воровства» CPU на момент замера нет.

Разбор готового скрипта `tune.sh` (с форума, набор `vps_tune_script`: `tune.sh` + `stat.sh`) по секциям для серверов с vpnbot_extra:

| Секция скрипта | Решение | Почему |
|---|---|---|
| conntrack | **взяли** (шаг 15) | единственное реальное слабое место |
| zram + swappiness 100 | не брали | swap почти не используется (12-21 МБ), давления на память нет; swappiness 10 у нас осознанно |
| TCP-буферы и очереди | **не брали, ухудшило бы** | у нас уже лучше: `rmem_max` 64 МБ (скрипт поставил бы 16 МБ), `somaxconn` 8192 (4096), `tcp_max_syn_backlog` 10240 (8192); BBR и fq уже есть; в отличие от conntrack, скрипт здесь «лучшее» не сохраняет |
| sniffing xray | не подходит | скрипт ищет конфиги x-ui и `/usr/local/etc/xray`, а у нас xray в контейнере, секция ничего бы не нашла |
| DNS-кэш dnsmasq | не брали | `resolved` и dnsmasq не запущены, DNS статический (8.8.8.8/1.1.1.1) - «шторма» нет; Docker не берёт `127.0.0.1` из resolv.conf для контейнеров, кэш не помог бы им; в апстримах IPv6-адрес при выключенном IPv6; `chattr +i` на resolv.conf может конфликтовать с этим гайдом |
| Nginx FD-лимиты | не подходит | nginx у нас в контейнере, на хосте его нет, секция пропускается |
| `stat.sh` | можно использовать | только чтение: RAM, zram, conntrack, PSI, топ процессов; наш сборщик (шаг 16) пишет то же самое во времени |

Вывод: **целиком этот `tune.sh` на серверы с vpnbot_extra запускать не нужно.** Если всё же запускаете - сначала
`sudo ./tune.sh --dry-run` и не допускайте секций TCP и DNS.

## Что затирает обновление бота (важно)

Правки 07, 08, 09 лежат **только на сервере** (`docker-compose.yml`, `dockerfile/php.dockerfile`, `app/`), в git форка их нет.
Автообновление у нас выключено. Если вы сделаете `make u` / `git pull` / обновление через меню, `app/` и compose могут вернуться
к исходным: просто снова запустите `audit.sh`, он покажет, что слетело, и повторите нужные скрипты (они безопасно

## Что осталось и не делается (по решению владельца)
